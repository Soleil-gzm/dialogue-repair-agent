## 1. Critical（必须立即修复）

### I-1：LLMPolicyError 异常路径 pending tokens 未入账

| 维度 | 内容 |
|------|------|
| **位置** | `runtime/loop.py:L111-L127` + `runtime/policy.py:L188-L207` |
| **描述** | `LLMPolicy.decide()` 在 `client.chat()` 成功后调 `state.add_tokens()`（policy.py:L199），但随后工具名校验失败或重复调用时抛 `LLMPolicyError`（L205/L207）。异常冒泡到 loop.py except 分支直接 break，**跳过 L127 的 `state.drain_tokens()`**。`_pending_tokens` 残留在 state 内未被消耗。 |
| **影响** | `AgentResult.tokens` 少记了这笔。评测主路径因 ledger 独立覆盖而隐藏，但独立使用 AgentRuntime 的场景会失真。 |
| **修复** | 在 loop.py except 分支里补一行 `state.budget.consume(tokens=state.drain_tokens())`，或改用 finally 模式统一 drain。 |
| **验证** | 给 LLMPolicy 注入返回已知 tool_calls 但工具名未注册的假 client，断言 `AgentResult.tokens` 等于实际 LLM 消耗。 |

### I-3：A4 臂判官模型未走 StageRoutedClient

| 维度 | 内容 |
|------|------|
| **位置** | `benchmark/agent_eval.py:L254-L258` |
| **描述** | 只有 A3R 用 `build_stage_clients`（内部调 `judge_settings()` 读 JUDGE_MODEL）；A4 和 A3L 都用普通 `DeepSeekClient(settings=settings)`。A4 的 LLMJudge 以 `stage="judge"` 调用，但普通 DeepSeekClient 不按 stage 路由——判官与生成共用同一个模型，违背 ADR D4"judge 与生成跨模型家族隔离"的设计意图。fingerprint 中 `judge_model` 也因此硬塞了 generate 侧的模型名。 |
| **关联** | ADR D4 明确规定 "stage 路由双模型是第一优先级"，当前代码里这条承诺名存实亡。 |
| **修复** | 所有需要 LLM 的臂统一走 `build_stage_clients`，只在 A3 时跳过。 |

### I-4：dialogue_key 三入口不一致（架构漂移）

| 维度 | 内容 |
|------|------|
| **位置** | `benchmark/fixtures.py:L91-L94` vs `runtime/state.py:L17-L20` vs `benchmark/canonical.py:L12-L16` |
| **描述** | 三处独立的"规范化 JSON + sha256"实现：<br>① `state.dialogue_key`：`json.dumps(sort_keys=True)`（紧凑无缩进）<br>② `fixtures.dialogue_key`：完全相同，注释自认"同构"<br>③ `canonical.stable_dump`：`indent=2 + "\n"`（带缩进换行）<br><br>三者对同一输入的哈希**完全不同**。架构设计 §8.7 明确"canonical.py 是唯一哈希入口"，但当前有三个入口。 |
| **风险** | 如果同一对话同时被两种方式哈希（state.key vs fingerprint.sha256），值不相等会增加排障难度；三处独立修改容易漂移。 |
| **修复** | 在 canonical.py 新增 `dialogue_key(obj)` 导出，state.py 和 fixtures.py 统一 import 它。同时**必须决定紧凑 vs 缩进哪个作为 canonical 格式**，改所有调用方。 |

## 5. 架构质量评价

### ✅ 做得好的地方
1. **测试分层**：单元/契约/集成/快照/边界五层完备，OSS 边界测试自证无私有文件外泄
2. **预算 + 死循环 + 回退三重保障**：loop.py 控制流设计稳健，四重预算无遗漏
3. **TokenLedger append-only + ledger/manifest 分层**：完全符合 ADR D7 判等与溯源分离原则
4. **eval/tools/runtime 依赖方向严格**：架构设计 §5 描述的依赖约束在代码中真实存在，无反向 import
5. **规范化哈希单点入口（canonical.py）**：设计意图好，只是 dialogue_key 没有跟进

### ⚠️ 设计执行有缺口的地方
1. **跨模型路由只做了一半**：A3R 是第一个消费者没错，但 A4 同样需要——设计文档说"A3R 是第一个消费者"，但 A4 的判官需求没被纳入同一条路
2. **评估器派生机制只做了"补丁级"**：源码哈希和 prompt 哈希能捕获实现变化，弥补了手写版本号的缺陷；但版本号本身还是硬编码，等于用两层机制做一件事，且只有其中一层派生
3. **函数内延迟 import 有选择性**：copy 在 run() 内延迟 import 是为了测试替换（有意图），hashlib 在 _args_fingerprint 内没有这个理由

### ❌ 没有发现的问题
- **安全漏洞**：API key 只从环境变量读取，永不入库、永不进日志
- **线程安全**：所有状态都在每次 run() 时新建，无全局可变状态
- **类型安全**：Protocol、dataclass(frozen=True)、显式 is not None 检查完备
- **错误处理**：网络错误重试、解析错误 fail-closed、判官异常保守回退全部实现
