## 一、定位与战略层

### D1｜项目定位：修复 Agent 还是质检 Agent？

- **决策**：当前定位为「质检 + 消融评测 Agent」，修复能力（rewrite_segment）是 Sprint 1 目标
- **依据**：两组消融共同指向"瓶颈在工具能力"——① A3 → A3L 只换决策者（规则 → LLM function calling），六类缺陷召回完全相同（macro 83.3% → 83.3%），成本却从 ¥0 涨到 ¥0.40/轮；② A3L → A4 决策不变、只把语义判官加进工具层，D1 从 0/20 拉到 20/20，macro 83.3% → 100%。当前工具集只有检查 + 回退，没有修复
- **面试防守**：Q「你这个 Agent 能修对话吗？」  
  A：当前版本是"诊断 + 保守回退"：检出即回退原文，宁可不改也不改坏（硬门禁优先于胜率）。rewrite 工具在路线图上，并且正是因为消融数据显示"瓶颈在工具不在决策"，我才把修复能力排在决策智能化之前——这个排序本身是实验驱动的。

### D2｜项目主方向：Harness 还是 Runtime？

- **决策**：主打 **Harness**（评测驱动层），Runtime 保持薄而稳
- **依据**：① 差异化资产全在 harness（不可变基线锁、intent-to-treat、stopped 分离、单变量消融）；② 目标 JD 中「评测体系」是唯一 ✅✅ 强项；③ 会"证明 agent 有效"的人远少于会"跑 agent"的人
- **边界**：runtime（loop/policy/registry/budget）够支撑消融即可，不追求框架级通用性
- **面试防守**：Q「为什么自己手写 runtime 不用 LangChain？」  
  A：当时已有 ToolRegistry 与状态追踪，手写复用成本低于学习框架；且 runtime 不是我的主战场，harness 才是——框架能替代 runtime，替代不了基线锁定和消融设计。（Sprint 2 的 LangGraph 对照实现补上"用过框架"的证据后，此答案升级为"两种都写过，知道各自适用边界"。）

### D3｜不做 Multi-Agent

- **决策**：单 Agent + 工具注册表 + 独立评估器，**不做 multi-agent**
- **依据**：① A3 vs A3L 消融显示决策层零增益——multi-agent 是把决策层拆得更碎，工具不变则预期只增成本不增质量；② 单对话修复不满足 multi-agent 的合理触发条件（任务需可按上下文隔离分解）；③ "自己评自己"问题已用「评估器独立于生成器」的更便宜结构解决
- **面试防守**：Q「为什么不做 multi-agent？」  
  A：我做过决策层消融：把规则决策换成 LLM function calling，宏观指标零增益，成本从 ¥0 涨到 ¥0.40/轮全量消融（132 条，单条约 ¥0.003）。这说明在工具集固定时决策层不是瓶颈。multi-agent 属于决策层复杂化，预期收益为负。如果哪天任务变成"需要多个互不污染的上下文窗口分工"，我才会引入。

### D4｜双模型按「生成侧 vs 评判侧」划分，不按功能划分

- **决策**：decide + rewrite 共用一个模型（生成侧），judge 独立一个模型（评判侧，跨模型家族）
- **依据**：① 自我偏好偏差——同模型既重写又判分会给自家输出打高分，胜率虚高（设计文档 §5.2 已预留此规则）；② 需求不同：rewrite 要创造性（temp 0.3–0.7），judge 要稳定复现（temp 0.0 + 强 JSON 契约）；③ 生成侧内部无利益冲突，共用即可
- **落地**：不做两个类，在客户端工厂按 stage 路由（`generate` / `judge` 两行配置）；配置允许指向同一模型，但此时必须在报告 limitations 声明"judge 与生成同模型"
- **环境分工**：公司机（4090）正式实验 = 本地 qwen 生成 + 异家族判官（线上 deepseek-chat 或本地 gemma/llama）；家里机（4060）= 单模型跑通链路，产物只做开发参考不进正式结论
- **面试防守**：Q「你一个 Agent 为什么用两个模型？」  
  A：LLM-as-judge 有自我偏好偏差，judge 和生成必须跨模型家族隔离，否则胜率虚高；这是我在设计阶段就写进偏差控制清单的，不是出了问题再补。

## 二、实验与数据层

### D5｜RAG 排期：接口先行，实现后移

- **决策**：本期不做 RAG 实现；`Retriever` 接口（`retrieve_guideline`）先定义进 registry，A5-RAG 臂只做设计占位
- **依据**：缺少真实人工编写的优质对话库；先保核心链路（修复闭环 + L3）跑通
- **检索材料方案**（后续启用时）：用**红线规则 / 业务合规口径 / 话术禁用词 / 承诺上限**作为检索语料——比"相似对话库"更权威、更不易被挑战来源
- **纪律**：实现之前简历不写 RAG；实现后按单变量原则挂 A5 臂，产出"有检索 vs 无检索"的胜率差 + CI
- **面试防守**：Q「你做过 RAG 吗？」  
  A：接口和对照臂设计已完成，检索语料选定了红线规则库方案，实现排期在修复闭环之后——排序依据依然是实验：当前瓶颈在工具能力，不在上下文来源。（诚实边界：实现前不说"做过"。）

### D6｜私有轨实验：公司数据 + 本地 Ollama

- **决策**：公开轨（程序化合成）之外增加私有轨（公司真实数据），用本地 Ollama 部署模型实验，**只发布脱敏聚合指标**
- **依据**：Benchmark 设计 §3.1 双轨 fixture 本就为此预留；真实数据上的复验能大幅增强公开轨结论的可信度
- **合规红线**：① 实验前内部报备；② 只展示聚合指标 + 缺陷类型分布，绝不展示原始对话 / 业务线名 / 字段值；③ 报告注明"私有轨数据不可公开，复现请用公开轨"
- **预期管理**：本地 7B–32B 检出率大概率低于线上模型——这个差距本身就是有价值的结论（模型能力下限对 Agent 效果的敏感性），照实报，不修饰
- **技术要点**：Ollama 走 OpenAI 兼容 API，deepseek 客户端改 base_url 复用；function calling 必须可用 → 选 qwen2.5/qwen3 系列

### D7｜跨环境（公司机/家里机）一致性

- **决策**：四层保障——依赖锁定、模型版本锁定、环境差异走配置不进代码、产物不合并只合并结论
- **要点**：
  1. `uv.lock` / requirements.lock 提交，两机统一安装；GitHub Actions（pytest + offline 复现断言）是最强保障——跨环境不兼容的代码进不了 main
  2. **Ollama 模型钉死完整 tag**（如 `qwen2.5:7b-instruct-q4_K_M`），核对 hash；模型名纳入 lock 指纹——模型版本漂移 = 评估器指纹变化，这是本项目最大的跨环境风险
  3. `.env`（gitignore）放本机差异（OLLAMA_BASE_URL、模型名、密钥），提交 `.env.example` 作契约；代码中永不出现"4060/4090"
  4. `output/`、ledger、cassette 不合并；实验 JSON 记录 machine id + ollama 版本；公开轨 offline 结果要求两机逐字节一致
- **落地分层（v1.2 补充）**：把"判等"和"溯源"拆成两个文件——混在同一个 lock 里，换机必然 verify 失败，lock 就从保障变成阻塞
  - `baseline_lock.json`（入库，**判等**）：只放跨机器必须一致的东西——输入 sha + 样本键集合 sha + seed + 分层字段、评估器指纹、生成侧模型 tag 与 prompt 版本、价格表版本、离线/回放档的臂产物 sha。任一项不同 = 结果作废
  - `run_manifest.json`（不入库，**溯源**）：machine id、OS、python 版本、依赖锁文件 sha、ollama 版本与模型 digest、起止时间、P50/P95、绝对路径。换机不同属正常，不参与 verify
  - `code` 段只溯源、不参与 verify：提交锁本身就会改变 HEAD，比 git_commit 会让 `--verify` 在锁入库后必然失败；真正的判等靠四元组指纹
  - 判定规则：`offline` / `replay` 档 artifact sha 必须逐字节一致；`live` 档 LLM 非确定，只要求四元组指纹一致，但结果必须带 manifest 才能进结论
- **评估器指纹必须派生，不能手写**：`rules_version` 要来自 `eval/rules.py` 常量，`judge_prompt_version` 要来自 `eval/judge.py` 的 `JUDGE_VERSION` 并附 prompt 文本 hash。此前 `benchmark/run.py` 手写的 `v1` 与 judge.py 的 `coherence-judge-v1` 已经不一致（S0 已改为派生）——手写常量等于锁不住"换尺子"
- **dirty 的锁不许入库**：`code.dirty=true` 时 `git_commit` 无法完整描述产生指纹的代码；S0 起生成即拒绝 dirty（`--allow-dirty` 仅临时调试），CI 断言入库锁为 clean，旧锁已按 v2.0 重建
- **面试防守**：Q「你在家和公司两台机器开发，怎么保证结果一致？」  
  A：显卡差异只影响速度不影响正确性，真正的风险是依赖版本和模型版本漂移。我用锁文件 + CI 复现断言管前者，用钉死模型 tag + 把模型名纳入基线指纹管后者——基线指纹机制本来就能捕获"尺子变了"，跨环境一致性是它的自然延伸。

## 三、路线图执行层

### D8｜Sprint 排序（修订版，与《agent改造路线图.md》v2.1 对齐）

> **修订记录 ｜ 2026-11-18**：原排序「S1 → 工程化 → RAG」细化为四级，新增 **S0 跨环境地基**；私有轨实验调整为 S1 并行工作流。修订理由：双机开发（家里 4060 / 公司 4090）使环境漂移成为最前置风险，CI 越早建越早受益；私有轨不依赖新功能，越早并行越早拿到真实数据结论。原排序保留在修订记录中作历史依据。  
> **修订记录 ｜ 2026-11-18（v1.2）**：① S0 收缩为「锁加固」——CI 与依赖声明已存在，实际只缺抽样指纹、评估器派生、dirty 断言、manifest 四项；② stage 路由双模型从 S0 移到 S1，因为 `generate` 阶段要等 rewrite 落地才有第一个消费者，提前搭抽象没有测试覆盖；③ S1 补两项前置：fixture dev/test 分离、L3 统一建在 `agent_eval` 之上并产出指纹。

| Sprint | 内容                                                                                                             | 对应 JD 缺口             |
| ------ | -------------------------------------------------------------------------------------------------------------- | -------------------- |
| S0     | 锁加固：抽样指纹（键集合 sha + seed + 分层）、评估器指纹改为代码派生、拒绝 dirty 入库、`run_manifest.json` 环境溯源、`uv.lock` + `.env.example` | CI/CD（地基）            |
| S1     | 前置：fixture dev/test 分离；rewrite_segment + stage 路由双模型 + L3 效果层（A2 臂、胜率 CI、McNemar、双向盲评、多样性指标，建在 `agent_eval` 上并产出指纹）+ replay 档位 + checkpoint ｜ **并行**：私有轨 Ollama 实验（合规报备先行） | 工具调用 / 评测体系 / 真实数据验证 |
| S2     | MCP server 封装、Docker Compose、OTel 可观测、（可选）LangGraph 对照实现                                                       | MCP / Docker / 可观测   |
| S3     | RAG **接口占位**：Retriever 协议 + retrieve_guideline 工具契约 + A5 臂设计文档；检索语料定向红线规则库；实现后移                                | RAG（诚实边界）            |

- **依据**：消融结论指向"先扩工具再谈决策"；CI 是跨机开发最强保障；MCP/Docker 成本低展示价值高；RAG 受材料制约，只占位不实现
- **修订规则**：每完成一个 Sprint，更新 Benchmark 设计文档（新增臂定义、缺陷-工具矩阵行），lock 指纹变化走 `--force --reason` 留痕
- **变更判定**：新需求先对照 D2（Harness 主方向）/ D3（不做 multi-agent），冲突的进待定池不排期

### D9｜简历与展示纪律

- **决策**：词汇映射（合成→工作流编排、Trace→可观测、预检→质量门禁等）只做「同义转述」；**未实现的词不写**（RAG、LangGraph、Dify 在各自落地前不上简历）
- **展示顺序**：README 首屏 = 修复闭环 + 可复现评测（不可变基线锁 / intent-to-treat / stopped 分离）+ 成本-效果前沿；作品集附 MCP 演示截图、一键 Docker、全绿 CI
- **人工标注**：κ 校准成本高，先用 judge 双向盲评顶 L3，人工校准作为 limitation 声明
