# Agent 文档中心

本目录是 `dialogue-repair-agent` 的全部设计、决策与操作文档入口。仓库是主工程 `agent/` 目录的开源切片，文档只描述当前仓库中可验证的代码能力。

## 1. 目录职责

| 目录 | 职责 | 放什么 | 不放什么 |
|---|---|---|---|
| `architecture/` | 描述“系统现在是什么、怎么运转” | 架构设计、模块与接口、Benchmark 评测设计 | 过程性讨论、已废弃方案 |
| `decisions/` | 描述“为什么这样定、接下来做什么” | 决策记录（ADR）、改造路线图 | 代码细节、指标定义 |
| `guides/` | 描述“怎么装、怎么跑、怎么排障” | 部署与运行指南 | 设计论证 |
| `archive/` | 保存历史版本与追溯记录 | 已过时文档、修订前快照 | 任何现行依据 |
| `notes/` | 记录过程中的疑问、术语与复盘 | 术语卡片、决策过程、实验复盘 | 权威定义、现行依据 |
| `reviews/` | 保存定期或专项代码审查报告 | 项目状态评估、代码审查、代码漂移检查、整改建议 | 权威设计定义、现行依据 |

新文档必须归入上述目录之一；不再向 `docs/` 根目录新增文件。`notes/` 中的内容**不得被现行文档当作依据**，结论升级后应迁入 `architecture/` 或 `decisions/`。

`reviews/` 下的报告按 `YYYY-MM-DD-主题.md` 命名，作为过程记录，不替代 `architecture/` 与 `decisions/` 的权威定义；报告中的问题关闭后，应把稳定的口径或决策回写到对应权威文档。

## 2. 文档规范

1. **版本头**：每份现行文档文首标注 `版本 / 最后修订 / 关联文档`。
2. **状态标注**：涉及能力时必须使用统一状态词——`已实现`、`部分实现`、`设计目标（未实现）`、`已移出范围`。
3. **单一事实源**：同一事实只在一份文档中定义，其他文档链接引用，不复制。
   - 指标定义、门槛、统计规则 → Benchmark 评测设计；
   - 模块职责、工具/CLI 契约 → 模块与接口说明；
   - 取舍理由与边界 → 决策记录 ADR；
   - 执行顺序与进度 → 改造路线图。
4. **链接规则**：使用相对路径；归档文档不参与冲突判定，也不得被现行文档当作依据。
5. **同步规则**：代码行为变化时，先改 Benchmark/接口文档，再改代码；合并前执行第 7 节校验。

## 5. 阅读路径

- **评审 / 面试准备**：架构设计 → Benchmark 评测设计 → 决策记录 ADR → 根 README。
- **开发新工具或新臂**：模块与接口说明 → Benchmark 评测设计（单变量原则）→ 改造路线图（排期）。
- **运行与复现**：部署与运行指南 → 模块与接口说明（CLI 与产物字段）→ 架构设计（可复现机制）。

## 7. 一致性校验

文档中的能力声明必须能被执行验证：

```bash
# 1. 全量测试（含开源边界自证）
python -m pytest

# 2. 复现冻结基线（CI 同款命令）
python -m agent.benchmark.run \
  --input agent/fixtures/public/base_v1.json \
  --arms A0 --verify-arm A0
```

提交前人工核对：

- 臂名只使用 `A0/A2/A3/A3L/A3R/A4/A4R/A5-RAG`（A1 已于 2026-11-19 移出主链），且每个臂标注实现状态；
- fixture 规模为 `base 12 / dev 30 / test 50 / defects 120`；
- CLI 参数与 [模块与接口说明](architecture/模块与接口说明.md) 一致；
- 未实现能力（A2、L3、replay、checkpoint 批量接入、Docker、MCP、OTel、RAG 实现）不得写成已完成；
- 所有相对链接可解析，归档路径不作为现行依据。
