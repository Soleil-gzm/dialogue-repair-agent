## 3. 代码审查

### 3.1 Critical（P0，修复前结论不可用）

#### C1. McNemar p 值计算错误，已产生「假显著」结论

- 位置：[l3_stats.py:160-217](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/l3_stats.py#L160-L217)
- 证据：
  - `_normal_cdf` 把 `erf(z)` 直接当 `Φ(z)`，漏掉 `z/√2`。实测 `_normal_cdf(1.6449)=0.989995`（正确 0.95）。
  - `_binomial_two_tailed` 实际是**正态近似**，但 `method` 标成 `"exact"`。
  - 本地 `logs/agent/compare_A4_A4R_noleak.json`：`n10=0, n01=4`，代码给出 `p=0.000407` 并标记「显著」；精确双侧二项 p 应为 `2 × 0.5^4 = 0.125`。
  - `compare_A3_A3R.json`：`2 vs 0` 给 `p=0.317`；精确值应为 `0.5`。
- 影响：所有基于 McNemar 的「显著/不显著」判断不可信；已有一条 A4 vs A4R 的假阳性结论被写入本地结果。
- 建议：`Φ(z)=0.5*erfc(-z/√2)`；`b+c<25` 时用 `math.comb` 精确二项；补已知数值测试；重算全部 L3 产物并撤回/修正假显著结论。

#### C2. A2 对照的 outcome 完全忽略 metric，A3 vs A2 主结论无效

- 位置：[agent_eval.py:565-590](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/agent_eval.py#L565-L590)
- 证据：`_collect_outcomes_a2(... metric ...)` 的 `metric` 形参从未使用；只做 `check_consistency`。D1（答非所问）、D5（重复空转）不改实体/结构，`check_consistency` 查不出，因此：
  - `metric=blocked` 时返回的是「保真度」而非「是否 fallback」；
  - `metric=no_leak` / `detected` 同样混用；
  - A2 原样回显未修复的 D1/D5 会被判成 success。
- 影响：`--compare A3,A2` 的 headline 结论被系统性高估；A2 的 `detected` 也只在 D2/D3/D4/D6 上有效（[agent_eval.py:402-413](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/agent_eval.py#L402-L413)）。
- 建议：按 metric 分流；对 A2 的最终输出接入与 A3 相同的 `check_coherence`/judge 复检；`blocked` 对 A2 明确为 False；用 fake client 构造 D1/D5 回归测试。

#### C3. 判官故障被记成「检出/阻断」，基础设施错误美化为模型能力

- 位置：[coherence.py:114-119](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/eval/coherence.py#L114-L119)、[agent_eval.py:338-345](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/agent_eval.py#L338-L345)
- 证据：`check_coherence` 捕获 judge 异常后返回 `C0_JUDGE_ERROR` 违规；`_absorb` 把它加入 `issues`；`run_arm` 随后把 `issues/seen_issues` 计入 `detected`，并可能触发 fallback（计 `blocked`），但不进 `failed`。
- 影响：判官超时/解析失败会抬高 A4/A4R 的检出率与阻断率；「判官是唯一增益」的结论可能被环境故障污染。
- 建议：单独统计 `judge_error`；不进入 `detected`/`repair_rate`；样本标记为 `failed` 或 `judge_error`；超过阈值时整轮结果作废；补故障注入测试。

#### C4. 「干净样本干预率」低估：stopped 与「误报后改写成功」未计

- 位置：[agent_eval.py:114-121](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/agent_eval.py#L114-L121)、[agent_eval.py:359-370](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/agent_eval.py#L359-L370)、[agent_eval.py:553-560](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/agent_eval.py#L553-L560)
- 证据：
  - `clean_intervention_rate` 文档写着「未跑完的样本按被干预计」，实现只加 `clean_flagged`（fallback）+ `clean_failed`（failed），**不含 `stopped`**。
  - 干净样本被误报后 `rewrite_segment` 成功、状态 accepted 时，`issues` 已被清空、`seen_issues` 非空，但 `clean_flagged` 不加，导致误伤漏计。
  - `_collect_outcomes` 的 clean outcome 同样把 `stopped` 当成功（`status not in ("fallback","failed")`）。
  - A2 干净样本只按一致性判「改坏」，未按「是否改动原文」判干预（[agent_eval.py:425-428](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/agent_eval.py#L425-L428)）。
- 影响：核心 headline 指标「干净样本干预率」系统性偏低，违反 R7「未跑完/异常中断按真实原因记录」。
- 建议：抽出单一 `is_clean_intervention(result)`：`status in (fallback, failed, stopped) or issues or seen_issues`；`run_arm` 与 `_collect_outcomes` 共用；补 stopped / 误报后修复 / A2 改写三类测试。

#### C5. 报告把 `--limit` 调试运行伪装成完整数据集

- 位置：[report.py:77-78](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/report.py#L77-L78)
- 证据：`n_defects` 硬编码为 `20 * len(defect_types)`、`per_type: 20`，`n_clean` 取 `arms[0]`。
- 影响：
  - 本地 `run_A4_final.json`（per_type 每类 1 条、manifest `limit=1`）经报告渲染会宣称 120 条；
  - 直接违反本轮规则「`--limit` 调试结果不得写入结论表格」；
  - 换 fixture 或扩样本后报告元数据自动错误。
- 建议：从各臂 `per_type[*].total` / manifest `extra.limit` 派生；渲染前校验各臂计数一致；不一致直接拒绝；加 `limit=1` 回归测试。

#### C6. 公开导出件依赖 PRIVATE 模块，开源发布即坏

- 位置：[agent_eval.py:476](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/benchmark/agent_eval.py#L476)、[oss_manifest.txt:125](file:///home/zimeng/work/projects/dialogue-repair-agent/agent/oss_manifest.txt#L125)
- 证据：`PUBLIC` 的 `agent_eval.py` 在 `compare_arms` 内 `from .l3_stats import ...`；`oss_manifest.txt` 将 `benchmark/l3_stats.py` 标为 `PRIVATE`（注释还称「含敏感信息」）。同时该文件已在主仓库被 git 跟踪。

### 3.4 分维度结论

**代码规范：** 类型标注、docstring、模块边界整体良好；测试数量充足但集中在下层单元，缺少新指标/统计的回归测试。无 lint/typecheck 门禁，建议补 `ruff` + `mypy`（至少 `benchmark`/`runtime`）。

**架构合理性：** 运行时、工具、评测三层基本清晰；主要问题是 `eval → runtime` 反向依赖、canonical 单入口失效、工具注册表为进程级全局可变状态（单进程 CLI 可接受，测试/并行需注意）。

**潜在 bug：** 统计函数、A2 metric、clean 口径、judge 故障、报告硬编码是确认级问题；其余为边界/异常路径问题。

**性能：** 每次调用新建 HTTP 客户端；`fingerprint` 重复读文件；client cache 无上限。对当前 120 条规模不致命，但会放大真实数据评测成本。

**安全：** 未发现密钥入库/日志泄漏；`.env` 已忽略。风险主要在：判官 prompt 直接拼接对话内容（真实数据下可被提示注入）、trace 可能落原始对话（PII）、`--out/--trace` 任意路径写入（本地 CLI，低风险）。

**可维护性：** 文档与代码状态表已经分叉；同一指标存在两套实现（run_arm vs `_collect_outcomes`）；硬编码较多（20、0.3、0.70、价格表版本），不符合「可调参数走配置」。
